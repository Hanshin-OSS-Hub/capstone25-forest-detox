# 01. 요구사항 명세서

## 1. 서비스 개요

### 1-1. 서비스명
디지털 디톡스 코치

### 1-2. 서비스 목적
사용자의 감정 상태와 휴대폰 사용시간 데이터를 바탕으로,  
AI가 디지털 습관 개선을 돕는 코칭과 챌린지를 제공하는 모바일 앱을 만든다.

### 1-3. 기술 스택
- 프론트엔드: Flutter
- 백엔드: Django + Django REST Framework
- 데이터베이스: SQLite
- 인증: Firebase 소셜 로그인
- 배포: AWS
- 개발 도구: PyCharm

### 1-4. 데이터 흐름 개요
Flutter 앱이 사용자 입력 데이터를 Django API 서버로 전송하고,  
Django는 SQLite에 저장한 뒤 JSON 응답을 Flutter에 반환한다.

기본 구조는 아래와 같다.

Flutter → Django REST API → SQLite

## 2. 사용자 유형

### 2-1. 일반 사용자
일반 사용자는 아래 기능을 사용할 수 있다.

- 홈 탭에서 감정 입력

### 2-2. 관리자

- 사용자 정보 조회

- 사용시간 데이터 조회

## 4. 로그인 및 인증 정책

### 4-1. 로그인 방식
로그인은 Firebase 소셜 로그인을 사용한다.

지원 대상:
- Google 로그인
- Kakao 로그인

### 4-2. 인증 흐름
1. Flutter에서 Firebase 로그인 수행
2. Flutter가 Firebase ID Token을 Django 서버에 전달
3. Django가 Firebase Admin SDK로 토큰을 검증
4. 검증 완료 후 Django 서비스용 인증 토큰 구조를 처리한다

### 4-3. 사용자 정보 저장
서버는 아래 사용자 정보를 저장한다.

- 이메일
- 닉네임 또는 표시 이름
- 로그인 제공자(provider)
- provider 고유 ID
- 프로필 이미지 URL
- 가입일
- 마지막 로그인 시각

### 4-4. 로그아웃 정책
로그아웃 시 아래를 모두 처리한다.

- Django 인증 상태 정리
- Firebase 로그아웃 처리

### 4-5. 회원 탈퇴 정책
회원 탈퇴 기능은 1차 개발 범위에 포함하지 않는다.

## 5. 감정 기록 정책

### 5-1. 감정 입력 방식
사용자는 감정을 아래 두 가지 방식으로 입력할 수 있다.

- 자유 텍스트 입력
- 원클릭 감정 버튼 선택

### 5-2. 원클릭 감정 버튼 기본값
초기 기본 감정 버튼은 아래 5개를 사용한다.

- 우울해
- 피곤해
- 즐거워
- 활기차
- 그저그래

### 5-3. 감정 입력 횟수
사용자는 하루에 여러 번 감정을 입력할 수 있다.

### 5-4. 대표 감정 기준
해당 날짜의 대표 감정은 **가장 최근에 입력한 감정**으로 본다.

### 5-5. 감정 저장 항목
감정 입력 시 아래 데이터를 저장한다.

- 사용자
- 입력 날짜
- 입력 시각
- 입력 방식(텍스트 / 버튼)
- 감정 값
- 원문 텍스트
- AI 분석 결과(선택)
- 메모 또는 요약(선택)

### 5-6. 감정 없는 날짜 정책
기록 탭에서 감정 기록이 없는 날은 **"감정 기록 없음"** 으로 표시한다.

## 6. AI 챗봇 정책

### 6-1. 챗봇 목적
AI 챗봇은 사용자의 감정 상태를 기록하고,  
짧은 위로 또는 디지털 습관 개선 방향을 제안하는 역할을 한다.

### 6-2. 챗봇 입력 방식
사용자는 직접 문장을 입력하거나,  
홈 화면의 원클릭 감정 버튼을 눌러 대화를 시작할 수 있다.

### 6-3. 챗봇 저장 대상
필요 시 아래 정보를 저장한다.

- 사용자 메시지
- AI 응답 메시지
- 대화 시각
- 감정 분석 결과
- 추천된 단기 목표 생성 여부

### 6-4. 챗봇과 감정의 관계
챗봇을 통해 입력된 감정은 감정 기록으로 연결될 수 있다.

### 6-5. 오늘의 팁 정책
오늘의 팁은 AI 실시간 생성 방식으로 제공한다.
사용자의 감정 상태 또는 디지털 습관 개선 방향을 바탕으로 생성한다.
오늘의 팁은 챌린지와 별개의 안내성 콘텐츠이다.

### 6-6. 챗봇 대화 저장 정책
챗봇 대화는 사용자 메시지와 AI 응답을 모두 저장한다.
저장 목적은 감정 기록 추적, 회고 기능 확장, 디버깅, AI 응답 품질 확인이다.

## 7. 목표 및 챌린지 정책

### 7-1. 주간 목표시간 설정
사용자는 매주 목표 사용시간을 설정한다.

예:
- 하루 4시간 이하 사용
- 하루 3시간 30분 이하 사용

### 7-2. 목표시간 저장 방식
목표시간은 **주간 목표시간 기준으로 저장**한다.  
필요 시 서버에서 일일 목표시간을 계산하여 사용한다.

### 7-3. 주간 난이도 설정
사용자는 매주 아래 난이도 중 하나를 선택한다.

- 초급
- 중급
- 고급

### 7-4. 난이도 갱신 시점
난이도는 **매주 월요일마다 새로 설정**하는 방식으로 운영한다.

### 7-5. 난이도 변경 반영 정책
주중에 난이도를 변경하더라도 **이번 주는 기존 목표를 유지**하고,  
**다음 주 생성 목표부터 반영**한다.

### 7-6. 단기 목표 생성 정책
- 단기 목표는 하루 단위로 관리한다.
- 단기 목표는 하루 3개를 생성한다.
- 사용자가 그날 처음 감정을 입력하면 AI가 단기 목표를 생성한다.
- 이미 생성된 단기 목표가 있으면 자동 재생성하지 않는다.
- 사용자는 별도 버튼을 통해 단기 목표를 재생성할 수 있다.
- 단기 목표 재생성은 하루 1회만 허용한다.
- 
### 7-7. 단기 목표 완료 정책
단기 목표 완료는 **사용자가 직접 체크**하는 방식으로 처리한다.

### 7-8. 단기 목표 난이도 정책
생성되는 단기 목표 난이도는 사용자가 설정한 주간 난이도를 초과하지 않는다.

예:
- 중급 설정 시: 초급 2개 + 중급 1개 또는 초급 1개 + 중급 2개
- 고급 설정 시: 초급/중급/고급 조합 가능
- 초급 설정 시: 초급 목표만 생성

### 7-9. 장기 목표 생성 정책
- 장기 목표는 월 단위로 관리한다.
- 장기 목표는 **3개**를 생성한다.
- 장기 목표 기간은 **매달 1일~말일** 기준으로 운영한다.
- 장기 목표는 디지털 습관 개선 중심으로 생성한다.

### 7-10. 챌린지 완료 정책
사용자는 단기/장기 챌린지를 완료 처리할 수 있다.

완료 시 서버는 아래 작업을 수행한다.

- 완료 상태 저장
- 포인트 지급
- 레벨 재계산
- 필요 시 레벨업 이벤트 기록

### 7-11. 단기 챌린지 상태 정책
단기 챌린지는 아래 상태값을 가진다.

- in_progress
- completed
- failed

기본적으로 사용자가 챌린지를 수행 중이면 in_progress 상태이다.
사용자가 완료 체크를 하면 completed 상태가 된다.
당일 자정이 지나도록 completed 상태가 되지 않으면 서버가 자동으로 failed 상태로 변경한다.

failed 상태가 된 챌린지는 기록 탭 캘린더의 해당 날짜 기록에 실패한 챌린지로 남는다.

### 7-12. 장기 목표 교체 정책
장기 목표는 진행 도중 교체할 수 없다.
사용자는 해당 월의 장기 목표를 그대로 유지한 채 수행한다.

## 8. 포인트 및 레벨 정책

### 8-1. 단기 목표 포인트
단기 목표 완료 시 아래 포인트를 지급한다.

- 초급: 10P
- 중급: 20P
- 고급: 30P

### 8-2. 장기 목표 포인트
장기 목표 완료 시 아래 포인트를 지급한다.

- 초급: 100P
- 중급: 200P
- 고급: 300P

### 8-3. 레벨 정책
레벨은 누적 포인트 기준으로 계산한다.

### 8-4. 레벨업 방식
레벨업은 **레벨 테이블 방식**으로 관리한다.

예시:
- Lv1 → Lv2 필요 포인트
- Lv2 → Lv3 필요 포인트
- Lv3 → Lv4 필요 포인트

이 방식으로 레벨별 필요 포인트를 테이블 형태로 관리한다.

### 8-5. 레벨 성장 정책
- 초기 레벨은 쉽게 올릴 수 있도록 적은 포인트를 요구한다.
- 레벨이 올라갈수록 필요 포인트를 점진적으로 증가시킨다.
- 일정 레벨 이상에서는 필요 포인트 증가를 멈추고 동결한다.

### 8-6. 레벨업 연출 정책
레벨업이 발생하면 축하 이벤트를 보여준다.

- 화면에 1~2초 동안 축하 효과 표시
- Flutter에서 시각 효과를 처리
- 백엔드는 레벨업 여부와 관련 데이터를 반환

## 9. 사용시간 정책

### 9-1. 사용시간 데이터 수집
휴대폰 전체 사용시간과 앱별 사용시간은  
Flutter 또는 모바일 네이티브 영역에서 수집한 뒤 Django 서버로 업로드한다.

### 9-2. 서버 역할
Django 서버는 아래 역할을 담당한다.

- 사용시간 저장
- 날짜별 집계
- 목표 대비 초과/달성 여부 계산
- 기록 탭 조회용 데이터 제공

### 9-3. 오늘 사용시간 표시
홈 탭에서는 사용자의 오늘 총 사용시간을 표시한다.

### 9-4. 진행률 표시
홈 탭에서는 목표 시간 대비 현재 사용시간을 바 형태로 시각화한다.

### 9-5. 앱 사용 Top5 정책
기록 탭의 앱 Top5 데이터는 **Flutter가 Top5를 정리한 뒤 서버로 전송**하는 방식으로 처리한다.

## 10. 기록 탭 정책

### 10-1. 기록 조회 기준
기록 탭은 날짜 선택형 상세 조회를 제공한다.

### 10-2. 날짜 선택 시 표시 데이터
선택한 날짜에 대해 아래 데이터를 제공한다.

- 대표 감정
- 감정 메시지 또는 상태 문구
- 총 사용시간
- 목표 달성 여부 메시지
- 당일 단기 목표 달성 현황
- 앱 사용시간 Top5

### 10-3. 목표 달성 여부 기준
해당 날짜의 총 사용시간이 그 주의 목표시간 이하이면 목표 달성으로 본다.

### 10-4. 달성 메시지
- 목표를 지킨 경우: 목표 달성 메시지 표시
- 목표를 지키지 못한 경우: 고정 격려 문구 표시

### 10-5. 미달성 메시지 정책
미달성 시에는 랜덤 문구가 아니라 **고정 문구**를 사용한다.

## 12. 외부 연동 정책

### 12-1. Firebase
Firebase는 소셜 로그인 인증에 사용한다.

### 12-2. AI 모델
AI 기능은 아래 용도로 사용한다.

- 감정 기반 단기 목표 생성
- 오늘의 팁 생성
- 챗봇 응답 생성

### 12-3. 푸시 알림

## 13. 비기능 요구사항

### 13-1. API 형식
모든 주요 API는 JSON 형식으로 통신한다.

### 13-2. 인증 보호
개인 데이터 관련 API는 인증이 필요한 구조로 만든다.

### 13-3. 시간대
기본 시간대는 Asia/Seoul 로 한다.

### 13-4. DB 정책
현재 프로젝트 데이터베이스는 SQLite를 사용한다.

### 13-5. 개발 원칙
- Django ORM 위주로 개발한다
- SQLite 전용 문법 의존을 최소화한다
- 나중에 다른 DB로 전환 가능하도록 구조를 단순하게 유지한다

### 13-6. 관리자 페이지
핵심 데이터는 Django Admin 에서 조회 가능해야 한다.
