# 04. 백엔드 구조 설계

## 1. 문서 목적

이 문서는 디지털 디톡스 코치 앱의 Django 백엔드 구조를 설계하기 위한 문서이다.  
현재 프로젝트는 SQLite를 사용하며, 초보자도 이해하고 유지보수하기 쉬운 구조를 목표로 한다.

이 문서에서는 아래 내용을 정리한다.

- Django 앱 구조
- 각 앱의 책임
- 앱별 모델 후보
- 앱별 API 후보
- 주요 데이터 흐름
- 구조 설계 원칙
- 추후 확장 방향

---

## 2. 구조 설계 기본 원칙

현재 프로젝트의 구조 설계 원칙은 아래와 같다.

1. 현재 사용 중인 Django 앱 구조를 최대한 유지한다.
2. 앱을 너무 잘게 쪼개지 않는다.
3. SQLite 기준으로 단순하고 직관적인 구조를 우선한다.
4. Django ORM 중심으로 설계한다.
5. 홈 / 챌린지 / 기록 / 설정 탭의 기능을 앱 책임 단위로 분리한다.
6. 인증, 사용량, 감정/챌린지 로직은 서로 역할이 섞이지 않도록 한다.
7. 나중에 기능이 커지면 앱을 추가 분리할 수 있도록 확장 가능성을 남긴다.

---

## 3. 현재 프로젝트 앱 구조

현재 프로젝트는 아래 구조를 기준으로 한다.

- `backend`
- `accounts`
- `usage`
- `wellness`

현재 단계에서는 위 구조를 유지한다.  
즉, 지금 당장 `wellness` 를 더 잘게 쪼개거나 새 앱을 대량으로 추가하지 않는다.

이유는 아래와 같다.

- 현재는 아직 초기 개발 단계이다.
- 초보자 입장에서 앱이 너무 많아지면 오히려 헷갈리기 쉽다.
- 기존 GitHub 구조를 최대한 살리는 것이 리팩토링 부담이 적다.
- 기능별 책임만 명확히 해도 충분히 안정적인 구조를 만들 수 있다.

---

## 4. 앱별 책임 정의

## 4-1. backend
`backend` 는 Django 프로젝트 전역 설정을 담당하는 폴더이다.

주요 역할:
- `settings.py` 에서 전체 환경 설정 관리
- 전역 URL 라우팅 연결
- ASGI / WSGI 설정
- 공통 인증 / REST / CORS / 환경변수 설정

직접 비즈니스 로직을 넣는 곳은 아니다.

---

## 4-2. accounts
`accounts` 앱은 사용자, 인증, 소셜 로그인 관련 기능을 담당한다.

주요 역할:
- 사용자 모델 관리
- Firebase 로그인 검증
- 사용자 프로필 정보 관리
- 로그인 제공자(provider) 정보 관리
- 현재 로그인 사용자 조회
- 로그아웃 처리

핵심 원칙:
- 사용자 관련 기능만 둔다.
- 감정, 챌린지, 사용시간 데이터는 넣지 않는다.

---

## 4-3. usage
`usage` 앱은 사용시간과 앱 사용 기록 관련 기능을 담당한다.

주요 역할:
- 주간 목표시간 저장
- 일일 총 사용시간 저장
- 날짜별 사용시간 조회
- 앱 사용 Top5 저장 및 조회
- 기록 탭의 사용량 데이터 제공
- 홈 탭 진행률 계산을 위한 기초 데이터 제공

핵심 원칙:
- 스마트폰 사용량 관련 데이터만 담당한다.
- 감정, 챌린지, 포인트 로직은 넣지 않는다.

---

## 4-4. wellness
`wellness` 앱은 감정, AI 챗봇, 챌린지, 포인트, 레벨, 오늘의 팁 등  
사용자 웰빙 중심 로직을 담당한다.

주요 역할:
- 감정 기록 저장
- 챗봇 대화 저장
- 감정 기반 단기 목표 생성
- 장기 목표 생성
- 챌린지 상태 관리
- 포인트 적립
- 레벨 계산
- 오늘의 팁 생성/저장
- 연속 달성일 계산

핵심 원칙:
- 사용자의 감정과 행동 교정 로직을 담당한다.
- 인증 정보와 사용량 원본 데이터는 직접 담당하지 않는다.

---

## 5. 화면 기준 데이터 책임 매핑

각 화면이 어떤 앱의 데이터를 사용하는지 정리한다.

| 화면 | 주 사용 앱 | 설명 |
|---|---|---|
| 홈 탭 | `wellness`, `usage` | 감정, 챗봇, 단기 목표, 연속 달성일, 오늘 사용시간, 진행률, 오늘의 팁 |
| 챌린지 탭 | `wellness` | 단기/장기 목표, 포인트, 레벨, 완료 처리 |
| 기록 탭 | `usage`, `wellness` | 날짜별 감정, 사용시간, 챌린지 현황, 앱 Top5 |
| 설정 탭 | `accounts` | 사용자 정보, 로그인 제공자, 로그아웃 |
| 알림 설정 | `accounts` 또는 `wellness` | 현재 프로젝트에서는 사용자 설정 성격이므로 추후 위치 확정 가능 |

현재 1차 구조에서는 알림 설정도 `accounts` 앱의 사용자 설정 범주에 포함하는 방향을 우선 고려한다.

## 6. 앱별 모델 후보

아래 모델명은 현재 설계 초안이며, 실제 구현 단계에서 소폭 바뀔 수 있다.

## 6-1. accounts 앱 모델 후보

### User
사용자 기본 계정 정보와 소셜 로그인 정보를 저장한다.

예상 역할:
- 이메일
- 닉네임
- provider
- provider_uid
- avatar_url
- 가입일
- 마지막 로그인 시각

### UserNotificationSetting
사용자 알림 설정을 저장한다.

예상 역할:
- 푸시 알림 on/off
- 사용시간 알림 on/off
- 야간 리마인더 on/off

---

## 6-2. usage 앱 모델 후보

### WeeklyUsageGoal
사용자의 주간 목표시간과 난이도 설정을 저장한다.

예상 역할:
- 사용자
- 시작 주차
- 종료 주차
- 주간 목표시간(분 단위)
- 주간 난이도(초급/중급/고급)

### DailyUsageSummary
하루 총 사용시간 요약 데이터를 저장한다.

예상 역할:
- 사용자
- 날짜
- 총 사용시간(분 단위)
- 목표 달성 여부
- 목표 초과 여부

### DailyAppUsageTop
하루 앱 사용 Top5 데이터를 저장한다.

예상 역할:
- 사용자
- 날짜
- 앱 이름
- 사용시간(분 단위)
- 순위(1~5)

---

## 6-3. wellness 앱 모델 후보

### EmotionLog
사용자의 감정 기록을 저장한다.

예상 역할:
- 사용자
- 날짜
- 시각
- 입력 방식(text / quick_button)
- 감정 값
- 원문 텍스트
- 감정 분석 결과

### ChatSession
한 번의 챗봇 대화 흐름을 묶는 세션 단위 모델이다.

예상 역할:
- 사용자
- 생성일시
- 연결된 날짜
- 대표 감정 또는 세션 요약(선택)

### ChatMessage
챗봇 대화 메시지를 저장한다.

예상 역할:
- 세션
- 발신자(user / ai)
- 메시지 내용
- 생성일시

### DailyChallenge
하루 단위 단기 목표를 저장한다.

예상 역할:
- 사용자
- 날짜
- 제목
- 설명
- 난이도
- 상태(in_progress / completed / failed)
- 포인트
- 생성 방식(AI / 재생성)
- 완료 시각
- 실패 처리 시각

### MonthlyChallenge
월 단위 장기 목표를 저장한다.

예상 역할:
- 사용자
- 대상 연월
- 제목
- 설명
- 난이도
- 상태(in_progress / completed)
- 포인트
- 완료 시각

### PointHistory
포인트 변동 이력을 저장한다.

예상 역할:
- 사용자
- 포인트 증감 값
- 사유
- 연결된 챌린지
- 생성일시

### UserLevel
사용자의 현재 레벨과 누적 포인트를 저장한다.

예상 역할:
- 사용자
- 현재 레벨
- 누적 포인트
- 마지막 레벨업 시각

### DailyTip
오늘의 팁을 저장한다.

예상 역할:
- 사용자
- 날짜
- 감정 기반 정보
- AI 생성 팁 내용
- 생성일시

### DailyAchievement
하루 전체 목표 달성 여부 및 연속 달성 계산을 위한 요약 데이터를 저장하거나 계산용으로 사용할 수 있다.

예상 역할:
- 사용자
- 날짜
- 하루 목표 전체 완료 여부
- 연속 달성 계산 기준 정보

## 8. 주요 데이터 흐름

## 8-1. 로그인 흐름
1. Flutter 에서 Firebase 로그인 수행
2. Firebase ID Token 을 Django 서버로 전달
3. Django 가 Firebase 토큰 검증
4. 사용자 조회 또는 생성
5. 로그인 성공 응답 반환

---

## 8-2. 홈 탭 흐름
1. 사용자가 감정을 입력한다.
2. 서버가 감정 기록을 저장한다.
3. 서버가 챗봇 메시지를 저장한다.
4. 오늘 단기 목표가 없으면 AI 기반으로 3개 생성한다.
5. 오늘의 팁을 AI 로 생성한다.
6. usage 앱에서 오늘 사용시간을 가져온다.
7. 목표 대비 진행률을 계산한다.
8. 홈 탭 통합 응답을 반환한다.

---

## 8-3. 챌린지 완료 흐름
1. 사용자가 단기 또는 장기 챌린지 완료 버튼을 누른다.
2. 서버가 챌린지 상태를 `completed` 로 변경한다.
3. 서버가 포인트 이력을 생성한다.
4. 서버가 누적 포인트를 갱신한다.
5. 서버가 레벨업 여부를 계산한다.
6. 결과를 응답으로 반환한다.

---

## 8-4. 단기 챌린지 실패 흐름
1. 챌린지가 당일 자정까지 `completed` 되지 않는다.
2. 서버가 해당 단기 챌린지를 `failed` 상태로 변경한다.
3. 기록 탭 날짜별 조회 시 실패한 챌린지로 보여준다.

---

## 8-5. 기록 탭 흐름
1. 사용자가 기록 탭에서 날짜를 선택한다.
2. 서버가 해당 날짜의 감정 기록을 조회한다.
3. 서버가 usage 앱에서 총 사용시간과 앱 Top5를 조회한다.
4. 서버가 그날의 단기 목표 달성 현황을 조회한다.
5. 목표 달성/미달성 메시지를 결정한다.
6. 날짜별 통합 응답을 반환한다.

---

## 9. 상태값 및 저장 규칙

## 9-1. 주간 목표시간 저장 규칙
주간 목표시간은 분 단위 정수로 저장한다.

예:
- 4시간 = 240
- 3시간 30분 = 210

---

## 9-2. 단기 챌린지 상태값
단기 챌린지는 아래 상태값을 사용한다.

- `in_progress`
- `completed`
- `failed`

설명:
- 기본 생성 상태는 `in_progress`
- 사용자가 완료 체크를 하면 `completed`
- 자정까지 완료되지 않으면 서버가 `failed` 로 자동 변경

---

## 9-3. 장기 챌린지 상태값
초기 버전에서는 아래 상태값만 사용한다.

- `in_progress`
- `completed`

장기 목표는 중간 교체를 허용하지 않는다.

---

## 9-4. 포인트 및 레벨 규칙
단기/장기 챌린지 완료 시 포인트를 지급한다.  
누적 포인트를 기준으로 레벨을 계산한다.

레벨 기준표 초안:

| 레벨 | 누적 포인트 기준 |
|---|---:|
| Lv1 | 0 |
| Lv2 | 50 |
| Lv3 | 120 |
| Lv4 | 220 |
| Lv5 | 360 |
| Lv6 | 540 |
| Lv7 | 760 |
| Lv8 | 1000 |
| Lv9 | 1300 |
| Lv10 | 1600 |

## 10. 파일 구성 원칙

각 앱에서는 아래 파일 구성을 기본으로 한다.

- `models.py` : 데이터 구조 정의
- `serializers.py` : 입력/출력 검증 및 JSON 변환
- `views.py` : API 요청 처리
- `urls.py` : 앱별 URL 연결
- `admin.py` : 관리자 페이지 등록
- `apps.py` : 앱 설정
- `migrations/` : 마이그레이션 파일

필요 시 아래 모듈을 추가할 수 있다.

- `services.py` : 비즈니스 로직 분리
- `selectors.py` : 조회 로직 분리
- `constants.py` : 상수 관리
- `tasks.py` : 추후 비동기 작업 또는 스케줄 작업용

초기 버전에서는 너무 복잡하게 나누지 않고,  
필요해질 때 점진적으로 파일을 분리한다.

## 11. 관리자 페이지 설계 방향

Django Admin 에서는 아래 데이터를 확인할 수 있어야 한다.

- 사용자 목록
- 감정 기록 목록
- 챗봇 세션 및 메시지
- 주간 목표시간
- 일일 사용시간 요약
- 앱 Top5 기록
- 단기/장기 챌린지
- 포인트 이력
- 사용자 레벨
- 오늘의 팁

관리자 페이지의 목적은 운영과 디버깅 보조이다.  
사용자용 핵심 기능을 관리자 페이지에 의존하지 않는다.

## 12. 현재 구조에서의 최종 결정

현재 프로젝트는 아래 구조를 유지한다.

- `backend`
- `accounts`
- `usage`
- `wellness`

즉, 현재 단계에서는 앱을 추가로 세분화하지 않는다.

다만 아래 조건이 생기면 추후 분리를 고려할 수 있다.

- `wellness` 앱의 코드가 지나치게 커지는 경우
- 챌린지/포인트/레벨 로직이 크게 복잡해지는 경우
- AI 관련 로직이 독립 서비스 수준으로 커지는 경우

그 전까지는 현재 구조를 유지하면서 역할만 분명히 한다.

---

## 13. 추후 확장 가능 구조

추후 프로젝트가 커지면 아래와 같이 확장할 수 있다.

- `challenges` 앱 분리
- `rewards` 앱 분리
- `ai_coaching` 앱 분리
- `notifications` 앱 분리

하지만 현재 단계에서는 분리하지 않는다.  
초기 구조는 단순하고 직관적인 형태를 유지하는 것을 우선한다.

---

## 14. 결론

현재 프로젝트의 백엔드 구조는  
기존 앱 구조를 유지하면서 각 앱의 책임을 명확히 분리하는 방향으로 설계한다.

최종 구조 요약:

- `accounts`: 사용자 / 인증 / 설정
- `usage`: 목표시간 / 사용시간 / 앱 Top5
- `wellness`: 감정 / 챗봇 / 챌린지 / 포인트 / 레벨 / 오늘의 팁
- `backend`: 전역 설정 / URL / 서버 환경

이 구조는 현재 SQLite 기반 초기 개발 단계에 가장 적합한 현실적인 구조이다.
